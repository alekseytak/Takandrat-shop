# Граница заказа и оплаты

Документ описывает, что магазин считает правдой, а что — лишь пожеланием
браузера. Читайте его перед любой правкой checkout, корзины, цен, остатков и
уведомлений о заказе.

## Что присылает браузер и что делает сервер

Клиент отправляет в Edge Function `admin-ai` (`action: 'create_order'`):

```json
{
  "telegram_id": 123456789,
  "customer_name": "Имя из Telegram",
  "phone": "",
  "address": "СДЭК, город, пункт выдачи",
  "items": [{ "product_id": "7", "quantity": 2, "size": "L" }]
}
```

Цены в этом запросе нет и быть не должно. Всё, что влияет на деньги, сервер
берёт из таблицы `products`:

| Что проверяется | Правило | Причина отказа |
|---|---|---|
| Корзина | не пустая, не больше 20 позиций | `EMPTY_ORDER`, `TOO_MANY_LINES` |
| Идентификатор товара | непустая строка или число | `BAD_PRODUCT_ID` |
| Количество | целое, от 1 до 20 | `BAD_QUANTITY` |
| Товар | существует в каталоге | `UNKNOWN_PRODUCT` |
| Продажа | `is_visible` не `false` | `HIDDEN_PRODUCT` |
| Остаток | сумма по товару не больше `stock_quantity` | `NOT_ENOUGH_STOCK` |
| Цена | положительное конечное число | `BAD_PRICE` |

Сумма заказа считается по цене из каталога и только так. Наличие проверяется
по товару целиком: два размера одного ремня — это две штуки со склада, а не
одна. Разные размеры остаются разными строками заказа, потому что по размеру
шьют изделие; одинаковые строки (тот же товар и размер) складываются.

Проверки живут в `supabase/functions/admin-ai/order.ts` — намеренно без Deno и
без Supabase, чтобы их можно было прогнать тестом:

```bash
npm run check:order     # 26 проверок, без сети и без базы
npm run check:telegram  # 16 проверок подписи, тоже без сети и без базы
npm run check:idempotency  # 16 проверок повтора, тоже без сети и без базы
```

## Кто заказывает — из подписи, а не из запроса

Покупатель определяется подписью Telegram, а не полем `telegram_id` из тела
запроса. Проверка живёт в `telegram.ts` (чистый модуль, без Deno и Supabase):

| Проверка | Отказ |
| --- | --- |
| Подписи нет вовсе | `INIT_DATA_MISSING` |
| Не строка, нет `hash`, `hash` не того вида, нет `auth_date` | `INIT_DATA_MALFORMED` |
| HMAC не совпал — подделали `user`, пересобрали строку, взяли чужой токен | `INIT_DATA_BAD_HASH` |
| Подпись старше суток или из будущего | `INIT_DATA_EXPIRED` |
| В подписи нет покупателя или его `id` не число | `INIT_DATA_NO_USER` |

Секрет подписи — `HMAC-SHA256(key="WebAppData", message=TELEGRAM_BOT_TOKEN)`,
подпись — `HMAC-SHA256(key=secret, message=data_check_string)`, где
`data_check_string` это все поля кроме `hash` и `signature`, отсортированные по
имени и соединённые переводом строки. Сравнение подписи идёт за постоянное
время, иначе её можно подбирать по времени ответа.

Если у функции не задан `TELEGRAM_BOT_TOKEN`, проверять нечем, и функция
отвечает `503 INIT_DATA_UNVERIFIABLE`. Это намеренный отказ: принимать
непроверенные заказы хуже, чем не принимать никаких.

Проверка доказано умеет падать: если отключить сверку подписи в `telegram.ts`,
четыре случая из шестнадцати краснеют.

## Что осталось открытым

**Дубль заказа: защита есть, на живой базе не проверена.** Покупатель
присылает `idempotency_key` — один на всю попытку оформления, поэтому повторное
нажатие после потерянного ответа возвращает прежний заказ, а не создаёт новый.
Решение принимает `idempotency.ts` (чистый модуль, 16 проверок), а в функции
остаётся один запрос к базе. Запрос ищет ключ в jsonb-поле `customer_info`:

```ts
.eq('customer_info->>idempotency_key', repeatKey)
```

Проверить это утверждение отсюда нельзя — Supabase недоступен, — поэтому в
`customer_info` пишется `idempotency_checked`. Если разбор jsonb не
поддержится, там окажется `false`, а заказ всё равно создастся: потерять заказ
хуже, чем получить дубль. Настоящая проверка — один раз вживую: два заказа с
одним ключом должны дать одну строку.

**Оплата подтверждается вручную.** Перевод на карту или кошелёк происходит
вне магазина. Ни статус заказа, ни уведомление владельцу не означают, что
деньги пришли. Так и написано покупателю на экране оформления.

## Как это проверяется

```bash
npm run check:order     # правила заказа: цена, количество, наличие
npm run check:telegram  # подпись Telegram: подделка, чужой токен, просрочка
npm run check:shop      # витрина, корзина, оформление — в настоящем браузере
npm run lint
npm run build
```

`check:shop` требует запущенного магазина (`npm run dev`). Он ходит по
магазину как покупатель: находит товар, кладёт в корзину, открывает
оформление, отправляет заказ и убеждается, что при недоступном сервере
покупатель видит понятную причину, а корзина остаётся на месте. Реальный
заказ не создаётся.

Проверки заказа умеют падать. Это проверено нарочной поломкой: если вернуть
цену «как прислал браузер», тест валит 5 проверок; если снять проверку
остатка — 2.
