# База магазина: как поднять заново и как проверить границу

## Что случилось

Проект Supabase магазина жив: 14 сентября служебным ключом проверено, что
таблицы `products` (6 строк), `orders` (0) и `users` (0) отвечают по REST.
Прежняя запись «проект не существует» была ошибкой наблюдателя: имя хоста
на этой машине иногда не разрешается, но это перемежающийся отказ DNS, а не
удаление. Доступность проверять запросом к таблице, а не разрешением имени.

Следствия, пока проект не восстановлен:

- каталог на витрине берётся из встроенного списка `src/constants.ts`, а не из
  базы: товары, цены и наличие из базы не приходят;
- заказы не создаются вовсе: функция `admin-ai` не развёрнута некуда;
- вход в админку не подтверждается: серверу некуда ответить, кто владелец.

Код магазина при этом цел. Всё, что нужно, — создать проект и выложить в него
схему и функции.

## Порядок

1. Создать проект в Supabase (регион ближе к покупателям).

2. Применить миграции по порядку — в SQL Editor или через `supabase db push`:

   - `supabase/migrations/20260101000000_init.sql` — таблицы, индексы,
     начальные товары, политика чтения каталога;
   - `supabase/migrations/20260914001000_rls_hardening.sql` — закрывает
     щедрые политики первой миграции. Без неё публичный ключ читает заказы и
     покупателей и позволяет вставлять заказы напрямую. Подробности — в
     комментариях файла.

3. Сказать магазину новый адрес и ключ: `VITE_SUPABASE_URL` и
   `VITE_SUPABASE_ANON_KEY` (на Vercel — в настройках проекта, локально — в
   `.env`). Публичный ключ новым проектом выдаётся заново, старый не подойдёт.

4. Выложить функции и задать им секреты:

   ```bash
   supabase functions deploy admin-ai
   supabase functions deploy telegram-bot
   supabase secrets set TELEGRAM_BOT_TOKEN=... TELEGRAM_ADMIN_CHAT_ID=... ADMIN_TELEGRAM_IDS=... API_KEY=...
   ```

   - `TELEGRAM_BOT_TOKEN` — обязателен. Без него функция отказывает в заказах
     (503): подпись Telegram проверить нечем.
   - `ADMIN_TELEGRAM_IDS` — id владельцев через запятую. Без него админские
     действия (`fetch_orders`, `fetch_stock`, поиск со скрытыми товарами)
     отказывают (503). Если не задать, берётся `TELEGRAM_ADMIN_CHAT_ID`, но
     только когда он положительный: у личного чата id совпадает с id человека,
     у группы — нет.
   - `API_KEY` — ключ для чата-консультанта. Без него чат отвечает 503 вместо
     падения.

5. Проверить:

   ```bash
   node scripts/check-rls.mjs     # публичный ключ видит только витрину
   npm run check:shop             # витрина и оформление в браузере
   npm run check:telegram         # подпись Telegram
   npm run check:order            # правила заказа
   ```

   Дальше один раз вживую: оформить заказ из мини-приложения Telegram и
   убедиться, что строка появилась в `orders`, а владельцу пришло уведомление.
   Повторить отправку с тем же ключом идемпотентности — вторая строка появиться
   не должна.

## Что проверяет `check-rls.mjs`

Скрипт стучится в базу тем же публичным ключом, что и браузер, и ждёт:

| Проверка | Ожидание |
| --- | --- |
| Видимые товары | читаются: витрина должна работать без входа |
| Скрытые товары | не отдаются |
| Заказы | не читаются |
| Покупатели | не читаются |
| Вставка заказа в обход функции | отказ (попытка заведомо неполная, данные не создаются) |
| Списание склада | отказ |

Почему это важно именно здесь: ключ, которым ходит браузер, публичный — он
лежит в бандле и виден любому. Он не секрет, и вся защита держится только на
правилах RLS в базе. Поэтому правила проверяются отдельно от кода.

## Про `ADMIN_SECRET`

В клиенте магазина лежал секрет `ADMIN_SECRET` (строка из 48 знаков), который
уезжал в бандл каждому посетителю. Сервер его никогда не проверял, так что
защищал он ни от чего, но строка попала в историю git. Если она где-то ещё
используется — считайте её раскрытой и замените. Из клиента она убрана: право
владельца теперь определяется подписью Telegram и списком id.
