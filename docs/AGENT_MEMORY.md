# Память проекта: что пробовали, что сработало, что нет

Файл ведут агенты. Правило простое: **после каждой сессии работы дописать сюда
строку**, а не полагаться на историю чата — чат закрывается, файл остаётся.
Порядок ведения — навык `/save` (`.agents/skills/save/SKILL.md`).

Отрицательный результат здесь стоит столько же, сколько положительный: он
экономит следующему агенту часы.

## Сработало — повторять

- **Ждать от базы её схему, а не читать миграцию.** `GET /rest/v1/` с заголовком
  `Accept: application/openapi+json` отдаёт колонки и типы всех таблиц одной
  командой. Почему: файлы миграций описывали базу, которой нет, и код по ним
  падал на схеме (`orders.items`, `customer_name`). Разошлось даже то, что все
  ключи в базе `bigint`, а функция объявляла их `uuid`.
- **DDL — личным токеном через Management API.** `POST
  /v1/projects/<ref>/database/query` с `Authorization: Bearer sbp_…` выполняет
  любой SQL. Почему: `execute_sql` пропускает только SELECT, прямое подключение
  идёт по IPv6 без маршрута, а токен решает вопрос целиком и без пароля базы.
- **Права отзывать у каждой роли, а не у PUBLIC.** В Supabase новые функции в
  схеме `public` по умолчанию выдаются ролям `anon` и `authenticated`. Почему:
  `REVOKE ... FROM PUBLIC` ничего не изменил, и публичный ключ создал заказ от
  чужого имени. Права смотреть так: `select proacl from pg_proc where
  proname='create_order'`.
- **Доказывать запись временными данными и убирать за собой.** Заказ `2×3900`
  записался на `7800` с позицией и размером, MCP-сервер прочитал заказ из двух
  позиций как «единиц товара: 3», после чего `DELETE` вернул заказов `0`,
  позиций `0`. Почему: пока данные не прошли через запись и чтение, «работает» —
  это предположение.
- **Проверять проверку мутацией и вслух признавать пустую.** Две проверки
  проходили ни за что: проба склада считала успехом `404` (функции в базе нет),
  а проверка MCP считала успехом текст ошибки базы. Теперь пустая проверка сама
  говорит, что ей не на чем падать.
- **Легаси anon-JWT для вызовов Edge Functions.** Новый `sb_publishable_…` шлюз
  отвергает (`401 Unsupported JWT algorithm ES256`). Почему: оформление заказа
  умирало на входе в функцию, а не в базе.
- **Мелочи среды, которые экономят часы.** На macOS нет `timeout` — брать
  `perl -e 'alarm N; exec @ARGV'`; нет `cat -A`; доступность проверять `curl`, а
  не `urllib` (он врал про отказы там, где curl отвечал 200).
- **После отката мутации проверять файл глазами.** Однажды `cp` из бэкапа вернул
  файл до правки, и правка чуть не ушла в отчёт как сделанная. Почему: `grep`
  после отката стоит секунду, а ложный отчёт — доверие.

- **Проверка, которая может упасть.** Каждую новую проверку ломали мутацией
  (портили проверяемое место) и смотрели, что она краснеет. Так пойманы
  настоящие дефекты: `null` в указателе версии, прозрачная шапка, `bg-brand/95`
  без альфы.
- **Настоящий браузер вместо догадок.** `scripts/shop-smoke.mjs` поднимает
  headless Chrome и читает вычисленные стили: класс в разметке есть, а правила
  для него нет — видно только так.
- **Сначала разведка шлюза, потом код.** `tools/oneprovider-probe.mjs`:
  спрашивать, что сервис умеет, а не писать под предполагаемый API.
- **Цвета Tailwind как `rgb(var(--x-rgb) / <alpha-value>)`.** Без тройки
  RGB альфа-модификатор молча не работает.
- **Версии вместо правок на месте.** Снимок + указатель + отказ без потерь:
  `tools/catalog-registry.ts`. Откат — это движение указателя.
- **Fail-closed на границе.** Нет `TELEGRAM_BOT_TOKEN` — заказ не создаётся
  (503), а не «создаётся без проверки».
- **Интеграция со стороны магазина.** Магазин отдаёт себя через свой
  MCP-сервер (`tools/mcp-shop.ts`), а не внешний проект знает его устройство.
  Проверено на Дрёме: `drema mcp` увидел 3 инструмента. Ни один внешний
  репозиторий при этом не менялся.
- **Переходный период ключей ломает вызовы функций.** Проект перешёл на
  асимметричные ключи подписи (текущий — ECC P-256, идентификатор
  `889f6d65-…`), а шлюз Edge Functions проверять ES256 не умеет: новый
  `sb_publishable_…` получает `401 Unsupported JWT algorithm ES256`. Легаси
  anon-JWT проходит. Вывод: пока проект не доведён до новых ключей целиком,
  клиент ходит легаси-ключом, а идентификаторы ключей из панели — не секреты и
  никуда не подключаются.
- **DDL через execute_sql закрыт.** Функция отвечает `Only SELECT queries
  allowed`: читать схему и определения функций можно, менять — нет. Значит
  починка схемы и функций требует пароля базы или личного токена доступа.
- **Права по умолчанию в Supabase выдают новые функции ролям anon и
  authenticated.** Отзыв `REVOKE ... FROM PUBLIC` не помогает: нужно отзывать у
  каждой роли поимённо. Поймано на живом: публичный ключ создал заказ от чужого
  имени. Права смотреть запросом `select proacl from pg_proc where proname=...`.
- **Личный токен открывает DDL там, где закрыт `execute_sql`.** Management API
  `/v1/projects/<ref>/database/query` выполняет любой SQL, включая DDL, и не
  упирается в IPv6. Это же путь для выкладки функций.
- **Заказ сейчас не создаётся: живая функция create_order сломана.** Она пишет в
  `orders.customer_name`, `orders.phone`, `orders.address` и
  `order_items.price_cents` — таких колонок в живой базе нет. Оба ключа получают
  один и тот же ответ 400 `column "customer_name" of relation "orders" does not
  exist`. Путь заказа: `src/components/Checkout.tsx` → `adminService.createOrder`
  → функция `admin-ai` → RPC `create_order`. Пока это не починено, магазин
  заказы не принимает.
- **DDL доступен через execute_sql.** В базе есть функция `execute_sql(query)`,
  закрытая для публичного ключа и открытая служебному. Через неё можно читать
  определения функций (`pg_get_functiondef`) и выполнять SQL — то есть чинить
  схему без пароля базы.
- **Спрашивать у базы её схему, а не читать миграцию.** Описание REST с
  заголовком `Accept: application/openapi+json` отдаёт колонки всех таблиц
  одной командой. Так выяснилось, что живая база богаче миграций в репозитории:
  9 таблиц, позиции заказа в `order_items`, а `orders.items` не существует —
  код и проверки, написанные по миграции, падали на схеме.
- **Проверять, что проверке есть на чём упасть.** Тест «скрытое не показывается»
  проходил вхолостую: в базе нет ни одного скрытого товара. Теперь проверка
  вслух говорит, что ей не на чем падать, и это не считается успехом.
- **Самовосстановление инструмента.** `tools/mail.mjs` перелогинивается, если
  токен пустой, нечитаемый или отвергнут: иначе одна порча файла ломает всё.
- **Долгие прогоны — в фон.** Проверочная сессия на несколько минут в
  foreground останавливает работу человека. Только background job.
- **Сначала посмотреть точный текст ошибки или файла, потом писать проверку.**
  Ожидание в проверке, написанное по памяти, — источник ложных провалов.

## Не сработало — не повторять

- **Доказывать неизменность обработки снимков числом, а не словом.** Копии
  товарных фото сверялись с оригиналами по размерам и по средней разнице
  пикселей: 1,6 из 255 — шум сжатия, изделие то же. Такую сверку можно
  предъявить владельцу, в отличие от «я аккуратно обработал».
- **`sips` не кодер.** В списке форматов он показывает webp, но файлов не
  пишет и молчит об этом, если погасить вывод. Рабочий путь — `sharp`.
- **Проверять проверку мутацией — на этом и поймали дыру.** Проба «скрытые
  товары публично не видны» проходила, потому что скрытых товаров в базе не
  было: пустой ответ читался как успех. Стоило перенести настоящий каталог и
  скрыть тестовый, как публичный ключ показал 10 товаров вместо 4 — и в базе
  нашлось правило `"Public products all"` с ролью `public` и условием `true`,
  то есть каталог был открыт на запись кому угодно. Мутация (вернуть старое
  правило и посмотреть, покраснеет ли проба) подтвердила, что новая проба живая.
- **Сверять форму данных базы с формой, которую ждёт отрисовка.** В базе одно
  поле `image_url`, а карточка читает `product.images.length` — на живых данных
  витрина падала целиком (React снимает дерево, покупатель видит пустую
  страницу), а на мёртвой базе работала, потому что у встроенного каталога
  `images` есть. Такую поломку видно только в браузере на настоящих данных:
  приводить строки базы к форме товара надо на входе, в загрузчике.
- **Доверять проверке, написанной под мёртвую базу.** Проверка витрины ждала
  название из встроенного каталога (`КАРТХОЛДЕР VEGETABLE`) с комментарием
  «база отсюда недоступна». База ожила, товары в ней другие, и проверка падала
  на ровном месте. Починил так, что ожидание берётся из базы, а встроенный
  каталог остался запасным путём. Урок: у проверки не должно быть зашитых
  данных, которые живут отдельно от источника правды.
- **Делегировать критичную работу субагентам в этой сессии.** Один субагент
  вернул пустой ответ и не сделал ничего (в репозитории нет его коммитов, в базе
  нет его правок), второй упал, не дойдя до конца. Что делать вместо: делать
  самому и проверять результат фактами — командой и её выводом, а не отчётом
  агента.

- **Tailwind через CDN и инлайн-конфиг.** Убрано: стили должны собираться
  PostCSS на сборке.
- **`!important` на `header { background: transparent }`.** Съедал фон липкой
  шапки; из правила исключён.
- **Просьба к модели «поправь фото, не меняя изделие».** Модели шлюза
  перерисовывают товар: черновики отклоняются, нужна пересъёмка.
- **Видео и голос через oneprovider.** Проверено дважды: генерация видео не
  настроена (503), голосовых моделей нет (404). Не тратить время.
- **Playwright с системным Firefox.** Не поддерживается: нужна своя сборка
  Playwright (~90 МБ). Системный Chrome — работает без закачки.
- **`failOnStartupError: false` в строке MCP.** Строка монтируется, но в сессии
  инструментов нет, и причина молчит. Ошибку надо делать видимой.
- **Проверять один пресет дважды в одном процессе.** Первый успешный прогон
  оставляет живой экземпляр, второй падает на «serverName уже занят». Один
  прогон на законченную правку.
- **`nslookup` и `web_search` на этой машине.** Не работают: доступность
  проверять `curl` или Node, искать — прямыми HTTP-запросами.
- **`timeout` в macOS.** Команды нет; ограничивать через
  `perl -e 'alarm N; exec @ARGV'`.

## Открытые вопросы

- Путь заказа целиком — `Checkout.tsx` → функция `admin-ai` → `create_order` —
  не пройден: для функции нужна настоящая подпись Telegram. По частям
  проверено: функция отвечает (403 без подписи), база заказ принимает, MCP
  читает заказ с позициями. Стык проверяется настоящим заказом из Telegram.
- Миграции в репозитории не описывают живую базу. Привести их в соответствие
  можно `supabase db pull` личным токеном — работа не сделана.
- Напоминание владельцу: JWT-секрет и служебный ключ побывали в переписке,
  ключ базы стоит перевыпустить при смене проекта.

- Служебный ключ базы лежит в `~/.drema/mcp.json` (права 600) и побывал в
  переписке — при смене проекта перевыпустить.
- Проект Supabase магазина жив (проверено ключом 14 сентября). Ошибка «проект
  удалён» держалась долго, потому что вывод сделан по отказам DNS, а они на этой
  машине перемежающиеся: проверять доступность запросом к таблице, а не
  разрешением имени.
- Водяной знак на фото отключён; изображения в `public/image.jpeg` нет.
- Мажорные обновления (React 19, Vite 7, Tailwind 4) не делались.
- Идемпотентность заказа и RLS проверены только на уровне кода, без живой базы.
