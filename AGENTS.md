# Магазин ТАК И РАТ: с чего начать агенту

Этот файл — входная точка. Прочитайте его целиком до первой правки: он короткий
и экономит часы на выяснение того, что уже выяснено.

## Что это

Витрина магазина кожи и одежды: каталог, корзина, оформление заказа,
подтверждение оплаты вручную, мини-приложение Telegram, админский экран.
Заказы и уведомления живут в Supabase (база плюс Edge Functions), витрина
раздаётся статикой, оплата идёт вне магазина.

Стек: React 18, TypeScript, Vite 5, Zustand, Supabase, Tailwind через PostCSS.
Локально поднимается одним процессом: `server.ts` (Express) на порту 3000.

## Проверки: запускать до и после правки

```bash
npm run lint              # типы, tsc --noEmit
npm run check:order       # правила заказа: цена, количество, наличие (26)
npm run check:catalog     # версии каталога: откат не теряет историю (15)
npm run check:telegram    # подпись Telegram: подделка, чужой токен, просрочка (16)
npm run check:idempotency # повтор заказа не создаёт второй (16)
npm run check:admin       # права владельца: заказы, склад, скрытые товары (30)
npm run check:mcp         # MCP-сервер магазина: инструменты, ответы, отказ (10)
npm run check:rls         # граница доступа к базе публичным ключом (нужна живая база)
npm run check:shop        # витрина, корзина, оформление, стили в браузере (26)
npm run build             # сборка
```

`check:shop` требует запущенного магазина и сам поднимает headless Chrome:

```bash
npm run dev &                          # или NODE_ENV=production node server.ts
npm run check:shop
SHOP_URL=https://... npm run check:shop   # проверка боевого адреса
```

Правило: проверка, которая не может упасть, бесполезна. Если добавляете
проверку — убедитесь, что она падает на сломанном коде (в этом репозитории это
делали мутацией: ломали проверяемое место и смотрели, что проверка краснеет).

## Границы, которые нельзя нарушать

Это не пожелания, а выводы из уже случившихся дыр. Каждая строка когда-то была
ошибкой в этом коде.

1. **Личность покупателя — только из подписи Telegram.** Не принимать
   `telegram_id` из тела запроса: раньше так создавали заказы от чужого имени.
   Проверка — `supabase/functions/admin-ai/telegram.ts`.
2. **Цена, количество и наличие — только из каталога базы.** Не верить тому,
   что прислал браузер. Правила — `order.ts`, проверяются `check:order`.
3. **Право владельца проверяет сервер.** Список владельцев — в переменных
   функции, а не в клиенте. Секрет в бандле не секрет.
4. **Публичный ключ Supabase не секрет.** Он виден каждому, кто откроет сайт,
   поэтому единственная защита данных — правила RLS в базе
   (`supabase/migrations/`). Никогда не полагайтесь на то, что клиент «не
   запросит» чужие строки.
5. **Повтор заказа не должен создавать второй заказ.** Ключ идемпотентности
   приходит от покупателя, решение принимает `idempotency.ts`.
6. **Товар нельзя придумывать.** Ни в текстах, ни в фотографиях: правка фото
   допустима, только если изделие не изменилось. Проверка — `tools/factory.ts`,
   факты — `docs/CONTENT_FACTORY.md`.
7. **Публикация контента — только по явному слову владельца** (`--approve`).
   Черновики не попадают в каталог сами.
8. **История каталога не стирается.** Версии только добавляются, «что сейчас на
   витрине» — отдельный указатель. Откат двигает указатель и ничего не удаляет:
   вернуться назад можно всегда. Логика — `tools/catalog-registry.ts`,
   проверки — `check:catalog`, команды — `tools/catalog.ts`.

9. **Интеграция живёт со стороны магазина.** Магазин сам рассказывает о себе
   через `tools/mcp-shop.ts`: любая платформа подключается к нему, а не магазин
   к платформе. Инструменты только на чтение — агент не меняет заказы и склад
   без слова владельца.

## Инструменты репозитория

- `tools/factory.ts` — фабрика контента: правка фото товара моделями со сверкой
  с исходником по списку свойств. Что шлюз умеет, а что нет — измерено и
  записано в `docs/CONTENT_FACTORY.md` (видео и голос этим шлюзом не делаются).
- `tools/catalog-registry.ts` — версии каталога: снимок, указатель, откат без
  потерь (чистые функции, проверяются без файловой системы).
- `tools/catalog.ts` — `status`, `record`, `rollback` по реестру версий.
- `tools/mail.mjs` — временный ящик для регистраций в сервисах: `init`,
  `address`, `list`, `read`, `wait`. Пароль и токен в `~/.takandrat/mail.json`
  (права 600, в репозиторий не попадают).
- `tools/oneprovider-probe.mjs` — разведка шлюза моделей: что отвечает, чем
  ограничено.
- `tools/mcp-shop.ts` — MCP-сервер магазина: состояние, товары, заказы. Только
  чтение, ключ из окружения, запускается платформой по stdio.
- `tools/mcp-smoke.ts` — проверка этого сервера отдельным процессом.
- `scripts/shop-smoke.mjs` — витрина и оформление в настоящем браузере.
- `scripts/check-rls.mjs` — граница доступа к базе публичным ключом.

Проектные навыки лежат в `.agents/skills/` (каталог, витрина, дизайн, выкладка,
база, контент, изображения, видео).

- `docs/AGENT_GUIDE.md` — руководство для агентов: подключение аккаунтов

- `docs/STATE.md`, если он есть, — состояние работ по сессиям.

## Подключение к магазину за пять минут

1. Склонировать репозиторий и поставить зависимости: `npm install`.
2. Скопировать `.env.example` в `.env` и заполнить: адрес и публичный ключ
   Supabase, ключи для функций. Секреты в репозиторий не коммитить.
3. Запустить `npm run dev` и `npm run check:shop` — если 26 проверок зелёные,
   магазин живой.
4. Прочитать раздел «Границы» выше — до первой правки, а не после.
5. Перед правкой заказа, подписи, прав доступа или оплаты — прочитать
   `docs/ORDER_AND_PAYMENT_BOUNDARY.md`: там записано, почему код устроен
   именно так.

  подпись не проверяет. Витрина обязана звать функции легаси anon-JWT (он же
  запасной ключ в `src/lib/supabase.ts`); в `.env` стоит именно он. Проверено:
  с легаси-JWT функция отвечает 403 сама (нет подписи Telegram), с новым
  ключом — 401 от шлюза, до функции дело не доходит.
- **Заказ создаётся.** Живая `create_order` была сломана дважды: писала в
  несуществующие колонки (`orders.customer_name`, `order_items.price_cents`) и
  объявляла ключи как uuid, тогда как в базе все ключи bigint. Функция
  переписана под живую схему (`supabase/migrations/20260915000000_fix_create_order_live.sql`):
  сумма считается по каталогу, имя и телефон — в `orders.customer_info`, адрес —
  в `orders.shipping_address`, цена позиции — в `order_items.price_at_time`.
  Проверено на живой базе: заказ 2×3900 записался на 7800 ₽ вместе с позицией и
  размером, тестовые данные удалены (заказов 0, позиций 0).
- **Право на создание заказа — только у служебной роли.** В Supabase новые
